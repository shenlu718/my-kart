# 技术路线：手感、去浏览器化、3D 建模

> 本轮由 5 个 agent 并行（4 路调研 + 1 路代码审查）产出的结论，**由主控逐条核验**后再写入本文。
> 【已核验】= 我亲自读代码 / 抓页面 / 跑命令确认过；【未取证】= 调研方明确说没拿到一手来源，别当结论用。

## 0. 一句话结论

「越改越乱」不是能力问题，是**结构问题**：真正决定手感的合并/超时/平滑逻辑全在唯一没有测试的那一层（`main.js` 688 行零测试），所以每次改动都没有防线。本轮先修了三个被代码审查抓到的真 bug（其中两个是 P0），再把调研结论固化成下面这张路线图；**接下来的每次改动都该先在这三个新防线上跑一遍**。

## 1. 本轮修掉的三个真 bug（都已验证）

| # | 问题（用户可见现象） | 根因 | 修法与验证 |
|---|---|---|---|
| ① | **手机刷新页面之后，手柄永久失灵**（面板一直显示未连接，只有键盘能开） | 手机页的 `seq` 是**页面级**计数器，刷新后从 0 重数；游戏侧只认"比上次大"，于是新包被当过期包**全部丢弃**，且丢弃时不刷新 `at` → `remoteIsFresh` 恒 false。按 16.7 包/秒算，要等 seq 追上旧值（约 60 秒）才恢复 | 手机页每开一次带一个 `sid`；`applyRemote` 在 `sid` 变化时当新会话重置序号（老页面没有 sid → 行为不变）。3 条测试 + 服务器端到端验证（POST 新 sid + seq=0 → SSE 正确透传） |
| ② | **体感"不跟手"**（倾斜手机到车轮转过去，中间有明显延迟） | 140ms 一阶平滑加在**合并之后**的 `turn` 上 —— 它本来是为键盘 0/1 跳变加的，却把体感一起糊了（50ms 到 30%、140ms 到 63%）；而油门轴完全不平滑，两轴时序还不一致 | 新增 `shapeTurn()`：**只有键盘那一路**平滑，手机/体感是连续信号直接进合并。3 条测试钉住"键盘 160ms 到六七成、手机第一帧给满" |
| ③ | 刷新电脑上的游戏页时，**车自己往前冲最多 800ms** | 服务器一直记着手机最后一次 POST（手机锁屏后仍是 `forward:1`）；游戏页刷新时 SSE 首帧把它推过来，游戏侧用本地时钟重新盖章 → 当成新鲜输入 | 服务器首帧改走 `freshSnapshotOrZero()`：过期快照清零。curl 实测：新鲜时首帧带 `forward:1`，等 1.2 秒后首帧变 `{forward:0,...,at:null}` |

测试数 121 → **128 全绿**。提交 `e32c907`。

## 3. 调研结论 A：怎么摆脱浏览器（用户："能不能自己写个软件"）

**先说硬墙（【已核验】官方文档）**：Windows 机器**做不了 iOS 原生包** —— Capacitor 官方明写 iOS 构建需要 macOS + Xcode（最低 Xcode 26.0）。所以"自己写个 App"在 iPhone 上，要么走 PWA，要么换 Mac。

| 方案 | 延迟 | 摆脱浏览器？ | 成本 | 结论 |
|---|---|---|---|---|
| **PWA**（manifest + 添加到主屏幕） | 不变 | ✅ 地址栏/标签页消失，从桌面图标直接进全屏 | 半天，0 依赖 | **本轮已做**（`phone/manifest.json` + 图标 + meta） |
| **Capacitor 壳** | 不变（传感器仍是 Web API 封装，【已核验】官方："This plugin is currently implemented using Web APIs"） | ✅ 彻底 | Android Studio + 真机调试；iOS 需 Mac | 只在安卓且 PWA 仍被"切后台/息屏"卡住时才做 |
| **全原生 Kotlin/Flutter** | 最低（原生 SensorManager 100Hz+，可走 UDP） | ✅ | 最高：UI 与逻辑重写一遍 | 现在不值得 |
| 换 WebRTC / WebTransport | **省不到肉眼可辨的毫秒**，而且要 HTTPS（MDN：WebTransport 也是 secure context） | ❌ | 高（信令/HTTP-3 服务端） | **不建议** |

**延迟的真账**（这条纠正了我之前的说法）：手机页发送节拍是 `setInterval(send, 60)`，即 **16.7Hz 不是 60Hz**，连续量（体感转向）因此有均摊约 30ms 的量化延迟 —— 这一项**大于局域网往返本身**。按键是事件驱动即时发送（`pointerdown` 立刻 `send()`），所以按键延迟只有 RTT。
→ 想更快，先改节拍（60ms→30ms 或"变化超阈值即发 + 最小间隔 16ms"），别急着换协议。

**已验证可用**：电脑端改成 Chrome/Edge 应用窗口（`--app=`）打开，没有地址栏/书签栏/标签页，看着就是个独立软件（本轮已写进 `dev-server.mjs` 的 `openBrowser`，找不到这两个浏览器则退回默认行为）。

**证书麻烦的真解法**（调研建议，未做）：用 mkcert 生成**固定的**根 CA 装到手机信任，叶子证书签一个稳定主机名而不是手写 IP —— 以后换网络只重签叶子，不用每次折腾。

## 4. 调研结论 B：3D 建模（把方块车换成真卡丁车）

**已核验的三个硬事实**：
1. `vendor/three/` 只有 `three.module.js` + `three.core.js`（r186），**没有任何 loaders** —— GLTFLoader 现在不在项目里，第一步是补文件而不是改代码。
2. `index.html` **没有 importmap**，`main.js:10` 用的是相对路径 `'../vendor/three/three.module.js'`。接 GLTFLoader 时必须同时加 importmap + 改这行 import，否则同一份 three 会按两个 URL 各实例化一次（`instanceof` 失效，极难查）。
3. 同工作区 `reference/chinese-can-fly-kart/public/maps/kenney/` 下有一套**现成可用的 Kenney GLB**（Starter Kit Racing，资产 CC0/代码 MIT），包含 `vehicle-truck-*.glb`、`track-*.glb`、`colormap.png` —— 零下载成本，可以立刻验证整条 GLB 管线。

**管线（推荐路径）**：
```
jsdelivr 取 three@0.186.0 的 3 个 addon 文件（GLTFLoader / BufferGeometryUtils / SkeletonUtils）
  → 落成 vendor/three/addons/{loaders,utils}/  ← 两者必须是兄弟目录，GLTFLoader 内部写的是 '../utils/...'
  → index.html 加 importmap：{"three": "./vendor/three/three.module.js", "three/addons/": "./vendor/three/addons/"}
  → main.js:10 改成 import * as THREE from 'three'
  → GLTFLoader 加载 GLB；旧的方块车保留为加载失败的 fallback（页面不能白屏）
```
不要用 Draco（要额外 vendor 3-4 个 decoder 文件，一辆 4-8k 面的车收益不抵复杂度）；也不要 importmap 直连 CDN（本项目"断网也能跑"是刻意设计）。

**建模契约（换模型绝对不能改这些，改了就撞物理与相机）**：
- 轮半径 0.25 m、轴距 1.13 m、半轮距 0.56 m、轮宽 0.18 m、圆柱 16 段
- 车头朝 −Z；原点在两轴中点的地面；四轮各自独立节点、轮轴沿 X
- 车轮动画只有三行代码，必须保留 `{mesh, pivot|null}` 结构：`pivot.rotation.y = turnSmooth * MAX_STEER`、`mesh.rotation.x = wheelRoll`
- 性能预算（引自 `reference/kart-royale/ART_DIRECTION.md`，本工作区已有）：**每车 6-12k 三角面、全帧 ≤250 draw call、每条硬边都倒角**（90° 硬边捕不到高光，是低模最典型的业余痕迹）；落到我们这辆车建议 4-8k、材质槽 ≤3

**素材许可坑（【已核验】）**：Kenney 明确 CC0 ✓；但 **Poly Pizza 抽查的两个 kart 模型是 CC-BY 3.0 不是 CC0**，商用/发布必须署名。Sketchfab 逐个看许可。

【未取证】Blender 官方文档在本环境全站 403，所以"导出面板逐项设置"只能给核对清单（+Y up / 单位米 / Apply Modifiers / 贴图 sRGB / 只导选中对象 / 导出后先拖进 gltf-viewer 验），不能当官方结论。

## 7. 未验证 / 待办

- 三个 bug 的修复都是**纯逻辑层验证**（测试 + curl）；真机上的表现仍要用户点头。
- PWA 的 standalone 在具体机型上的表现未测（MDN 把 manifest `display` 标为 Limited availability）。
- Capacitor 壳内自定义 scheme 是否算安全上下文（能否免掉自签证书）**未核验** —— 那是"能不能彻底告别 HTTPS 麻烦"的唯一关键。
- 手机热点的实际可达性、延迟抖动：现有数据只有用户一次实测（≤50ms）。
