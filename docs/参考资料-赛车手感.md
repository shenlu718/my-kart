## 0. 最重要的一条（先看这个）

**参考项目自己测量并承认：臂长随速度变长，与速度感是反的。**【一手】
`reference/kart-royale/src/core/Feel.ts` 头部：

> 玩家报告：「全速时它并不像仪表盘那么快。」
> 直线全油门实测两端：**46 km/h → fov 52.4 / 臂长 6.08 m；106 km/h → fov 58.9 / 臂长 6.47 m**。
> 于是两件事浮出来：视野在整个可用速度区间只开了 **6.5°**，而臂长反而**变长**了
> —— **两者都在对抗速度感，而不是强化它**。
> 眼睛读速度靠的是**画面边缘的光流**，它在这三件事发生时上升：
> **① 镜头变广 ② 相机降低 ③ 相机靠近掠过的物体。**

它的「猛」预设 `PUNCHY`【一手】：

| 参数 | SHIPPED（出货值） | PUNCHY（猛） |
|---|---|---|
| `fovSpeed`（静止→全速多开多少度） | 5.0 | **15.0** |
| `armDistSpeed`（全速时臂长变化，**负=收近**） | +0.55 | **−0.9** |
| `armHeightSpeed`（全速时相机高低变化） | −0.22 | **−0.55** |
| `streak` / `rush` / `fringe`（后处理速度线/径向模糊/色散） | 1 / 1 / 1 | 1.6 / 1.8 / 1.35 |

**→ 对我们**：上一轮我把 `ARM_DIST_SPEED` 设成 **+1.2 米（随速度拉远）**，方向是**反的**。
正确做法是**收近 + 降低 + 视野大开**。这一条是本次调研最直接可用的结论。

### 1.2 车辆物理全量常量【待核验，来自子代理实读】

来源 `src/kart/Kart.ts`(2370) / `Tyre.ts`(195) / `Suspension.ts`。

**转向**（我们已采用的部分，值可核对）

| 常量 | 值 | 作用 |
|---|---|---|
| `MAX_STEER` | 0.55 rad (31.5°) | 静止满舵角 |
| `WHEELBASE` | `DEFAULT_SUSPENSION.halfBase*2` | 轴距（由悬挂半轴距推出） |
| 阿克曼 | `rackYaw = clamp((fwd/WHEELBASE)*tan(steerAngle), ±maxYaw)` | 偏航率 ∝ 车速 |
| `maxYaw` | `24 / max(5, |fwd|)` | 高速封顶，防"要求一个抓不住的弯" |
| `STEER_RATE_LOW/HIGH/FREE` | 10.5 / 5.6 / 15（输入单位/秒） | **齿条不对称**：向内打死慢、回正/反打快 |

> ⚠ **齿轮比不对称**这条我们**没有**：我们只有一个 `TURN_SMOOTH_TAU=0.14` 对所有方向。
> 参考的理由：对称速率会造成「**480 ms** 的方向切换延迟」（作者实测），而"车应该在你要求的一瞬间变向"。

**轮胎侧向抓地曲线 —— 漂移能成立的原因**【待核验】

```
侧向 μ(s)：s ≤ peakSlip 时  μ = peakMu·sin(π/2 · s/peakSlip)      ← 四分之一正弦上升
            s > peakSlip 时  μ = lerp(peakMu → slideMu, smoothstep) ← 衰减到一个低平台
```

| 轮胎 | peakSlip | slideSlip | peakMu | slideMu |
|---|---|---|---|---|
| 前轮 | 0.14 | 0.60 | 1.68 | 1.15 |
| 后轮 | 0.16 | 0.78 | **1.95** | 1.38 |

- **后轴峰值更高是刻意的**：若后轴更低，每个快弯都会瞬间打转；**漂移必须靠显式压后轴抓地来产生**
  （`DRIFT_REAR_GRIP_IN=0.98 / OUT=0.6`），而不是靠脆弱的默认偏置。
- **峰值之后的下降段**才是漂移"甩出去并保持甩出去"的物理来源；没有它，一松手就弹回。

**漂移状态机 25 个常量**【待核验】——与旧笔记一致，另补：`STRAIGHT_BAIL=1.0s`、
`TURN_ASSIST=6.0 / TURN_RELIEF=2.2 m/s²`、`THRUST=3.0 m/s²`、`ARM_TIME=0.8s`。

**悬挂/重量转移**【待核验】：刚度由质量反推 `k = m·g/(4·restCompression)`；
侧倾惯量 `m·0.55²`、俯仰 `m·0.78²`；惯性力矩 `m·aLat·comHeight`（`comHeight=0.34`）；
防倾杆 `58 N·m/rad/kg`；侧倾上限 `0.26 rad`；最终由轮胎的 `loadSensitivity` 把
"载荷压到外侧轮"变成抓地下降。

**碰撞/空中**【待核验】：墙 `WALL_RESTITUTION=0.28`（重撞直接 `releaseDrift`）；
车-车 `KART_RESTITUTION=0.42`（各施加一半冲量，`|Δy|>1.5` 跳过以免立交桥上下互推）；
`HOP_SPEED=3.05`、`airTime>0.06s` 才判定腾空、`AIR_STEER=1.5 rad/s`。

### 1.3 相机：全量常量 + 构图数学 + 舒适边界

**构图数学（frameSubject，L1273-1308）**【一手，我逐行读过】

给定相机位置 `eye` 与车 `k`，求一条视线使车投影到 NDC `(fx, fy)`：

```
_pt = k.position + up·SUBJ_UP          // 参照点（车体中部，不是地面）
_dir = normalize(_pt - eye)
_right = normalize(cross(_dir, up)); _up = cross(_right, _dir)
_dir 绕 _up 转 +atan(fx·tanH)          // 先偏航
_dir 绕 新_right 转 −atan(fy·tanV)     // 再俯仰
aim = eye + _dir · |_pt - eye| → lookAt(aim)
```
> 两次旋转不严格可交换，但在这些角度下耦合误差不到 1/5 度（原注）。

**关键边界**【一手】：`MAX_LAG=0.455`(26°) 滞后上限、`MAX_ARM_RATE=2.0`（+`_LOST=3.2`）摆速上限、
`MAX_SLEW=2.0` 整体自转兜底、`FRAME_ANG_RATE=0.85` 构图角变化率、`FRAME_X_MAX=0.30` 横向硬上限、
`FRAME_Y=-0.19`（+速度 −0.05）车压在下半屏、`SUBJ_UP=0.55`。

**⚠ 两处文档/源码不一致**【一手，我 grep 复核过】——**教训：注释不是值，读源码**：

1. `Camera.ts` 的 `FOV_SPEED`(L72) / `ARM_DIST_SPEED`(L89) / `ARM_HEIGHT_SPEED`(L94)
   **是死代码**：全文件只在声明处出现，实际取值来自 `Feel.ts`（见 §1.5）。
2. `MAX_ARM_RATE` 注释写「2.7 rad/s 是 155°/s」，**值却是 2.0**；`MAX_SLEW` 注释写「3.1/178°」，**值也是 2.0**。

### 1.4 速度感的正确做法：`Feel.ts` 可热改调节台【一手，全文读过】

**这是一个"给玩家（开发者）在游戏里现场调参"的台子**，正是我们缺的"反馈线"：

```js
__feel.punchy()          // 一键切到"猛"预设
__feel.reset()           // 回出厂值
__feel.set({fovSpeed: 9})// 单项改
__feel.show()            // 打印当前值，可直接贴回代码
```
实现要点：`feel` 是一个模块级对象，`installFeel()` 用 `Object.defineProperty` 把它挂到
`window.__feel`，读属性返回当前值、写属性下一帧生效。

它的自我说明【一手】：
> 「把测量出来的数字当手感来猜是不对的，所以这个东西是拿来**开**的：
> 改一个值，继续玩，相机下一帧就跟着变。」

**→ 对我们**：我们有 `src/kart-math.js` 的纯函数 + 面板，但**没有**这种"下一帧生效"的统一调参口。
这是一个低成本、高收益、且完全对齐用户痛点的东西。

### 1.5 赛道与 `bend`（"提前构图"的原料）【待核验】

- 赛道**不是**中心线点列，而是**曲率表**：`LEGS: [长度m, 转角deg][]` → 0.25m 网格写 κ
  → 30m 半窗 ×2 遍盒模糊（生成 clothoid 过渡）→ 积分并重归一使总转角恰为 −2π
  → 按真实 3D 弧长重采样成 **0.5m 等弧长站位表**。
- `bend` **不是曲率**，而是「**前方 26–68 m 处路面切线方向**」与「相机右轴」的点积：

```
bend = clamp( normalize(y=0(tangent at t + ahead)) · camRight , -1, +1 )
ahead = 26 m + 34 m × sp        // 速度越快看得越远
```
- 然后 `corner = clamp(0.72·(yawRate·speed/9.0) + 0.50·bend·calm, -1, 1)`，
  再经 τ=0.15 阻尼 + 3.0/s 变化率上限。

**→ 对我们**：我们现在的"领入弯道"是**反应式**（靠车身滞后）。参考是**预判式**（看前方的路）。
要做预判，最小实现是：给车加一条**前视射线**去采样"前方路面方向"——不一定需要整张曲率表。

### 1.7 手机当手柄：参考实现读透后的收获【一手，本轮逐行读了它的 4 个文件】

位置：`reference\chinese-can-fly-kart\phone\`（`index.html` 34 行 / `controller.mjs` ~131 行 /
`controls.mjs` 16 行 / `protocol.mjs` 33 行）+ `src\remote\{PhoneController,RemoteState}.ts`。
四种输入并存：**触摸按钮、浮动/固定摇杆、体感倾斜、物理手柄**；只有**横屏**才允许驾驶。

**协议（`protocol.mjs`，33 行里有三条关键设计）**

| 设计 | 原话/实现 | 我们 |
|---|---|---|
| **`seq` 序号必填** | `Number.isSafeInteger(p.seq) && p.seq>=0`，不合规整包丢弃 | ✅ 已补（`applyRemote` 丢过期包，有测试） |
| 输入超时 600ms | `export const INPUT_TIMEOUT = 600` | 我们 800ms（同量级） |
| 按钮用**单调计数器**而非布尔 | `gas`/`banana` 是 `SafeInteger` 计数器 —— 布尔量丢一次就永久错，计数器变了就知道有新事件 | 我们用 60ms 心跳重发状态，效果等价 |
| `steer` 是**连续轴** [-1,1] | 不是 ±1 开关 | ❌ 我们只有 ±1（见下） |

**体感倾斜的正确数学（`rollDegrees`，三条坑）**
```js
// 把重力投影到【当前屏幕平面】——横屏/竖屏要分别处理
const x = cos(beta)*sin(gamma), up = sin(beta);
const screenX  = x*cos(a) + up*sin(a);
const screenUp = up*cos(a) - x*sin(a);
if (hypot(screenX, screenUp) < 0.15) return null;   // ① 手机几乎平放桌面：重力给不出稳定的滚转角
return atan2(screenX, screenUp);                    // ② 必须 atan2，不能用 asin
```
> ② 的原注：**「atan2 保留整个圆周；asin 在 90° 处折叠，欧拉角换分支时会跳」** —— 这条我们自己写体感时一定会踩。
> ① 是我完全不会想到的守卫：平放桌上时体感值会乱跳。
> 还有 `screenAngle()` 把 `landscape-secondary` 归一成 270（浏览器之间不一致），
> `steerFromTilt(deg, range, invert)` 带 **2° 死区**再按 `range`(10–40°，可调) 归一。

**摇杆的去死区写法（`stickPosition`）**：死区后要**重新归一**，否则永远到不了满舵
```js
steer = |axis| < .08 ? 0 : sign(axis) * (|axis| - .08) / .92;
```

**中位校准（体感必需）**：不是"按一下就取当前值"，而是**手机稳定 160ms 才取零**
（`candidate` 变化 >3° 就重新计时）；有独立校准键；**屏幕方向一变就作废重校**。

**松手事件必须听三个**：`pointerup` / `pointercancel` / **`lostpointercapture`**，
且**不听 `pointerleave`**（捕获后手指滑出不该算松手）。
→ 我们漏了 `lostpointercapture`，导致**按钮卡在"按着"、车一直冲**（本轮修掉，真 bug）。

**其他值得抄的**：驾驶时申请 `navigator.wakeLock.request('screen')`（否则玩到一半息屏）；
`ping/pong` 测并显示延迟；`type:'safety'` 由主机强制停车；配对用 URL hash 里的
`#12位id.48位key` 令牌（**同一网段谁都能发输入**，我们目前无鉴权）。

**我们暂不做的**：体感（需 HTTPS + 自签证书 + 安卓也要安全上下文）、摇杆/模拟转向、
配对鉴权、道具键。理由：前两个是独立工作量，后两个要等游戏有对应内容。

## 3. 经典理论

### 3.1 Marco Monster《Car Physics for Games》(2003)【一手·外，纵向部分】

```
纵向阻力  Fdrag = −Cdrag·v·|v|      Cdrag = 0.5·Cd·A·rho ≈ 0.5·0.30·2.2·1.29 ≈ 0.4257
滚动阻力  Frr   = −Crr·v            Crr ≈ 30·Cdrag ≈ 12.8（原作者自述存疑）
加速度    a = F/M
积分      v += dt·a;  p += dt·v     ← 顶速由方程自然浮现，**不需要设上限**
重量转移  Wf = (c/L)·W − (h/L)·M·a;  Wr = (b/L)·W + (h/L)·M·a
驱动力    Fdrive = Tengine·xg·xd·n/Rw   (n≈0.7 传动效率)
示例      448Nm × 2.66 × 3.42 × 0.7 / 0.34 ≈ 8391 N；后轮静重 7350 N；转移 2940 N；a ≈ 4.9 m/s²
```

**⚠ 横向力 / slip angle 模型没抓到**（页面在纵向部分即被截断，无分页）——【未核验】。
不要把"Marco Monster 的侧向公式"当已知事实引用。

> **→ 对我们**：我们的 `nextSpeed` 是**手搓的分段线性**（ACCEL/COAST/BRAKE/TURN_DRAG）。
> Marco 的方案更"物理"，但也更复杂。**当前阶段不必换**；但有一条值得抄：
> **顶速不该是"设上限"，而是由阻力自然浮现**——我们把 `MAX_SPEED` 硬钳住，
> 好处是可预测、测试稳定，坏处是"油门到底"和"快到底"之间没有过渡感。

### 3.2 Brian Beckman《The Physics of Racing》【一手·外，标题与要点】

- **Part 1 重量转移**：转移源自惯性作用于高于地面的 CG，效果正比于 **CG 高度**；
  只需轴距 / CG 高 / 静态配重 / 轮距即可算四轮法向力。
- **Part 7 摩擦圆（Circle of Traction / Traction Budget）**：
  纵向力与侧向力**共用**一个抓地上限（摩擦圆），用掉一个就少一个。
- **Part 21/22 Magic Formula（Pacejka）** 纵/横向；**Part 10 Grip Angle**。

> **→ 对我们**：**摩擦圆**是"刹车时不能满舵、满舵时不能全力加速"的物理来源。
> 我们现在刹车与转向**互不影响**（`nextSpeed` 里两者独立），所以"过弯收油"是硬编码的 `TURN_DRAG`。
> 若要更进一步（漂移），摩擦圆是正确的骨架。

## 5. 对我们项目的可执行清单

### 优先级 A：立刻能做（低成本、高收益、有参考背书）

1. **`ARM_DIST_SPEED` 改负**（收近而非拉远）+ `armHeightSpeed` 降低相机 + 视野增益加大。
   → 依据 §0，参考实测证明当前方向反了。
2. **加 `window.__feel` 式统一直调口**：把相机/手感的可调量集中到一个对象，
   浏览器控制台能改、下一帧生效、能 `show()` 回贴代码。
   → 依据 §1.4，这正是"一个人调参很麻烦"的解药。
3. **转向齿条不对称**：向内打死慢、回正/反打快（参考 10.5/5.6/15 对；理由：对称会造成 ~480ms 切换延迟）。
   → 依据 §1.2。

### 优先级 B：需要一点新基础设施

4. **前视采样 → 预判式构图**：一条前视射线取"前方路面方向"，替换/补充现在的反应式滞后。
   → 依据 §1.5，是最小版的 `bend`。
5. **轮胎侧向抓地曲线 + 后轴压低** → 漂移；**摩擦圆**把刹车/转向耦合起来。
   → 依据 §1.2 + §3.2。
6. **曲率表 / "是否在弯里"**：不再问车身。

### 优先级 C：暂不做

7. 多车碰撞、道具、AI 赛车线、定点数学（联机）、后处理速度线（`streak/rush/fringe`）、
   地表差异、手机触控。→ 都需要各自的基础设施，且当前没有需求。
