## 一、追逐相机（chase camera）

### 1.1 最重要的一条：不要用位置弹簧【一手】

参考实现 `reference/kart-royale/src/game/Camera.ts` 的头部注释：

> **There is no positional spring**: a spring chasing a moving kart settles with
> a standing error of `|v| × T`, which silently rewrites the rig geometry at speed.
> All the smoothing lives in the bearing and in the scalars, where it can be reasoned about.
>
> （不用位置弹簧：追一个移动目标的弹簧会留下正比于速度的稳态误差，
> 这会在高速时悄悄改写相机几何。所有平滑都放在方位角和标量上，
> 因为在那里它们才是**可以被推理**的。）

**我们犯的错**：把平滑加在了 `camera.position.lerp(...)` 上。
后果就是用户实测看到的「峰值速度一变大，车突然变得很小」。

**正确架构**：

```
① 一个标量：方位角 armYaw（镜头"坐在车后方哪个方向"）
     它弹簧式地追车的朝向，滞后量用两个边界封顶
② 位置由方位角解算：eye = 车 - 方位×距离 + 上×高度
     平滑全在方位角和标量上，位置精确算出
③ 屏幕构图是解算的，不是涌现的
```

### 1.2 关键参数表【一手，数值已 grep 核验】

| 常量 | 值 | 作用 |
|---|---|---|
| `HEAD_TAU` | 0.17 s | 方位角弹簧时间常数（漂移时 0.09、切弯 0.05、低速巡路 0.20） |
| `MAX_LAG` | 0.455 rad（26°） | **滞后硬上限**，对底盘计 —— 保证玩家看得见前方 |
| `MAX_ARM_RATE` | 2.0 rad/s | 方位角转动速率上限（超限时抬到 3.2） |
| `FRAME_ANG_RATE` | 0.85 rad/s | 构图角变化速率上限 |
| `MAX_SLEW` | 2.0 rad/s | 相机整体自转上限（最后的兜底） |
| `ARM_DIST` | 5.6 m | 臂长基准 |
| `ARM_DIST_SPEED` | 0.55 m | 臂长随速度的增长（**故意很小**） |
| `ARM_HEIGHT` | 1.15 m | 离 pivot 的高度 |
| `FOV_BASE` | 50° | 垂直视野（16:9 时水平 79°，"已发行的卡丁车多在 75–80°"） |
| `FOV_SPEED` | 5.0° | **视野随速度张开这么多** |

**注意最后两行**——"速度感"主要靠 **FOV 张开**，而不是靠臂长变化。原注释：

> an arm that grows to match holds the subject at a constant size in every shot
>
> （让臂长去跟着匹配，会把主体在每一帧里都固定成同一个大小。）

### 1.3 屏幕构图是**解算**出来的【一手】

> 给定最终眼睛位置，有一个唯一的视角轴能把车放在屏幕的指定位置上 ——
> 就是把 eye→kart 向量旋转 `atan(ndc × tan(halfFov))`。
> **所以构图不是"希望如此"，而是"构造出来"，主体不可能跑出画面。**

具体做法：构图角 `compAng` → 换算成 NDC → 钳制在 ±0.30。
垂直方向基准 `FRAME_Y = -0.19`（车在画面偏下，把上半屏让给前方的路）。

### 1.4 工程上的其他通行做法【二手】

位置弹簧并非没人用，只是都给它加了**滞后上限**：

| 引擎 | 做法 |
|---|---|
| Unreal `SpringArmComponent` | `CameraLagSpeed`（跟多快）+ **`CameraLagMaxDistance`（钳制分离距离）** + `CameraRotationLagSpeed` |
| Godot `SpringArm3D` | `length` + shape 的 sweep cast 做位置回撤 |
| Unity Cinemachine `Framing Transposer` | "与 Follow 目标保持固定**屏幕空间**关系" |

**共同点：都在给位置滞后加约束。** 而参考项目选择了更彻底的方案——不给位置加滞后。

## 二、漂移（drift）

### 2.1 物理模型：三级简化【一手 + 二手】

**第一级（理论起点）**：把轮胎力拆成**纵向力**和**侧向力**分别求解。
纵向力（牵引/制动/滚阻/风阻）决定速度，侧向力（轮胎侧向摩擦）决定转向。
来源：Marco Monster《Car Physics for Games》（2003）【二手】

**第二级（侧向抓地曲线 —— 漂移的关键）**：

```
μ 随滑移角：先按 1/4 正弦升到 peakSlip 达到峰值 peakMu，
            再用 smoothstep 衰减到一个更低的"滑动平台" slideMu
```

**峰值之后的下降段就是漂移之所以能成立的原因**——它让后轮"甩出去并保持甩出去"，
而不是一松手就弹回来。【一手，`Tyre.ts` 注释原文】

**第三级（我们项目缺的正是这个）**：前后轴需要**不同的抓地峰值**。

| 轮胎 | peakSlip | slideSlip | peakMu | slideMu |
|---|---|---|---|---|
| 前轮 | 0.14 | 0.6 | **1.68** | 1.15 |
| 后轮 | 0.16 | 0.78 | **1.95** | 1.38 |

【一手，grep 核验】

**为什么后轮峰值必须更高**（原文）：

> 若前轴峰值更低，车会先推头（可救，读作"我要求太多"）；
> 若**后轴峰值更低，则每个快速弯都会瞬间打转**。
> 漂移必须通过**显式把后轴抓地按比例压下去**来产生，而不是靠脆弱的默认偏置。

### 2.2 低速保护：一个必须写的下限【一手】

```
beta = atan2(vLat, max(|vLong|, 1.4))     // 纵向速度取 1.4 m/s 下限
```

**少了这个下限**：车静止时被侧向一推，滑移角直接跳到 90°，
表现为"发车格上的幽灵滑动轮胎"。

### 2.3 「漂移 → 加速」的参数结构【一手，已 grep 核验】

```
DRIFT_ENGAGE_STEER   = 0.13        触发漂移的最小转向量
DRIFT_TIERS          = [0.55, 0.95, 1.9]        三档蓄力时间（秒）
DRIFT_BOOST_TIME     = [0, 0.95, 1.8, 3.0]      三档加速持续（秒）
DRIFT_BOOST_STRENGTH = [1, 1.12, 1.25, 1.36]    三档速度倍率
DRIFT_SLIP_OUT       = 0.06        反打时的滑移设定值
DRIFT_SLIP_IN        = 0.2         向内打死时的滑移设定值
DRIFT_SLIP_GAIN      = 2.6         滑移控制器增益（1/s）
DRIFT_MAX_YAW        = 26          偏航率上限（"无论误差多大都转不飞"的兜底）
DRIFT_CARRY_TIME     = 0.8 s       蓄力时钟的保持窗口
DRIFT_RELEASE_GRACE  = 0.3 s       松开按键的去抖窗口
```

**蓄力时钟不是匀速走的**【一手】：

```
driftTime += dt × (0.85 + 0.4×q) × onRoad × corner
  q       : 由实测滑移角归一化（普通漂移 ≈1.01×，深漂移 ≈1.25×）
  onRoad  : 车轮离地/上草的惩罚（两轮压路肩 ≈40% 速率）
  corner  : 只在弯道内计时，直道漂移不充电
```

### 2.4 六个已经踩过的坑【一手，均在源码注释里有记录】

| # | 坑 | 后果 | 修法 |
|---|---|---|---|
| **1** | 漂移的偏航是**自维持**的 | 一个抖动的按键把"一次漂移"保持了 35 秒、整圈 84% 横着走 | **"我是否在弯里"不能问车身**，要查赛道中心线曲率表 |
| **2** | 两个宽限窗口打架 | 蓄力被"付两次钱" | `DRIFT_CARRY_TIME` 只管 tier 0；一旦升档绝不适用；**永不延迟付费** |
| **3** | 滑移设定值符号写反 | 玩家想救车的瞬间命令了更深的漂移 → **打转** | 反打(0.06) 必须 **<** 向内(0.2) |
| **4** | 物理滑移角堆太大 | 只买到拖拽，**没有任何视觉收益** | 可转向性靠操纵杆直接项，不靠堆滑移 |
| **5** | 起漂阈值 > 弯道实际需求 | 玩家觉得"要先有专门知识才能起漂" | 按赛道半径实测反推阈值（0.2 → 0.13） |
| **6** | **低档奖励太便宜** | 玩家"点一下就放"刷低档（实测刷到 19 个蓝档，价值超过放弃的 4 个紫档） | 压平底档、拉长高档（档 3 时长 = 档 1 的 3.2×） |

**坑 6 的教训最值得记住**：

> 前一代的旧表 tier1 只值 +0.10s，**小于"滑一秒"的成本**，
> 导致漂移圈比不漂移还慢 2.6 秒。
>
> —— **一个"感觉很好"的机制，如果算下来是亏的，玩家一定会发现。**

### 2.5 任天堂的做法（官方对照）【二手】

Mario Kart Wii 的 mini-turbo 是一个**整数计数器**：

```
横向摇杆输入有 -7..+7 共 15 档
漂移方向一侧按住 ≥3 档时：每帧 +5
否则：每帧 +2
分两档：蓝火花（标准）/ 橙火花（超级，仅卡丁车）
释放时给最大速度 +20%
```

**和参考项目对比**：结构完全同构（蓄力时钟 + 分档 + 释放增益），
只是参考项目用了**秒**而不是**帧**作为单位。

## 三、调参方法论：用测具，不要用肉眼

**这是整份文档里最重要的一节。**

参考项目有 13 个测试 harness，其中两个直接对应我们的痛点【一手，已核验存在】：

| 测具 | 回答什么问题 |
|---|---|
| `tools/camera-probe.mjs` | **camera lag、swing（恶心指标）、framing、settle time** |
| `tools/drift-bench.mjs` | **漂移圈是不是真的比干净圈快？** |
| `tools/steer-test.mjs` | 车是不是朝输入的方向走？ |
| `tools/fps-bench.mjs` | 能不能稳住 60fps，瓶颈在 CPU 还是 GPU |
| `tools/tear-hunt.mjs` | 有没有撕裂或半渲染的帧 |

**原作者的一句话总结**：

> The harnesses are the point of this repo more than the game is.
>
> （这个仓库里，测具比游戏本身更重要。）

### 为什么这对我们特别关键

用户的原话：

> 「速度的衰减，加速度的衰减，镜头的偏移的速度，镜头偏移的加速度，
> 赛车过弯漂移撞击赛道的打击感……我感觉我一个人优化手感的话非常麻烦。」

**答案不是"参数少一点"，而是"别用感觉去调"。**

| 感觉 | 对应的可测指标 |
|---|---|
| "镜头晃得我恶心" | camera-probe 的 `swing`（度/秒）和 `settle time` |
| "漂移没意义" | drift-bench 的圈速对比（漂移圈 vs 干净圈） |
| "车怎么又变小了" | camera-probe 的 `framing`（车占屏比例） |
| "过弯掉速太狠/不够" | drift-bench 的档位直方图 + 单圈时间 |

**有一个"仪器会撒谎"的教训也值得记住**【一手，来自参考项目 README】：

> 两个测具曾给出自信、精确、完全虚构的数字
> —— 一个把相机相对向量当成世界点来投影；
> 另一个的帧率旋钮根本没接上，制造出"17 倍帧率依赖"的假象。

**结论：先验证仪器，再相信读数。**

## 五、对我们项目的结论

### 已经做对的

- ✅ 相机改为「方位角弹簧 + 位置精确算」，去掉了位置弹簧
- ✅ 用最短弧处理环形角度
- ✅ 所有速率限制都以「时间常数 × dt」表达（帧率无关）
- ✅ `kart-math.js` / `keys.js` 的纯函数分层，35 个测试

### 还缺的（按依赖顺序）

| # | 缺什么 | 为什么它排这个位置 |
|---|---|---|
| **1** | **滑移物理**（速度方向 ≠ 车头方向） | 漂移的地基。没有它，相机跟随朝向和跟随行驶方向是同一件事 |
| **2** | **漂移状态机 + 蓄力分档** | 依赖 1 |
| **3** | **赛道中心线曲率表** | 坑 1 的正解——"是否在弯里"必须查路，不能问车 |
| **4** | **测具**（camera-probe / drift-bench） | 否则上面三个都只能靠感觉调 |
| 5 | FOV 随速度张开 | 比臂长变化更有效的"速度感"来源 |

### 一条方法论

> **先把一个机制做到"能测"，再谈调参。**
>
> 参考项目的作者不是靠反复试参做出了那个手感 ——
> 他有 `drift-bench` 告诉他"漂移圈快了 2.6 秒"还是"慢了 2.6 秒"。
> **没有这条反馈线，"调参"就只是随机游走。**
